Кейс

Idle-Clicker на roblox-ts

Полноценная сервер-авторитетная idle-игра: экономика, бой, прогрессия. Нижняя оценка — не «демка», а production-система, где каждая из систем защищена от читов, масштабирования чисел и потери данных.

Два стора (SSoT + mirror)

Серверный obbyStore — единственная правда; клиент clientStore — зеркало + монстр + сессии. Синхронизация через Broadcaster с контрактами аргументов.

Экономика на BigNum-строках

Все игровые числа — строки с мантиссой и экспонентой: без потери точности за пределами 2⁵³, overflow-защита, кэши парсинга и форматирования.

Бой: оптимистик + валидация

Клики идут мгновенно (оптимистично), сервер считает DPS, комбо и капы, а Broadcaster исправляет расхождения. Античит тихо отсекает спам.

20+ мета-систем

Артефакты и миссии, сейджи, кланы с боссами, кристаллы с трансферами и подтверждёнными покупками, асценсия, резонанс, навыки, оффлайн-прогресс, лидерборды, ачивки.

Полный цикл данных

Миграции схемы, глубокий санитайзер повреждённых/читерских данных, профильное сохранение с handshake и защитой от утечки сессий, автосейв с троттлингом.

UI: React + 60 FPS

Виртуализация списков, объектный пул, апдейты через refs, react-reflex selectors без лишних ре-рендеров, токены по дизайн-системе без bare-чисел.

Инжиниринг

Реальные проблемы, которые я закрыл

Не маркетинговые бейджи, а конкретные технические кейсы с обоснованием решений. Кликни — раскроется деталь. (Все цифры и файлы реальны, в этом репозитории.)

01

Точность чисел на масштабе idle-игры

BigNum-строки вместо number, которые ломались на 2⁵³
  • Игровые числа хранятся как строки "1.23e15" и живут в математике без потери точности;
  • Случай с 32-битным побитовым wrap-around, который уронил бы сервер на степенях 3e9+, решён арифметическим powerBinary + overflow-стражем;
  • Parse-кэш (512) и готовые суффиксы K/M/B/… — читабельно и не нагружает GC на хот-пате.
02

Сервер-авторитетность и античит

Клиент шлёт только намерения, сервер считает всё
  • Единый 5-шаговый паттерн хендлеров: guard → валидация конфига → расчёт на сервере → проверка условий → атомарный dispatch;
  • Типизированный middleware на @flamework/networking: per-player/event окна, мягкий дроп пакетов (без киков, false-positive не накажут винта);
  • Лимиты согласованы с реальной скоростью игры (напр. клики 60/с против реального CPS + кликеров).
03

Оптимистик-клики против пессимистик-покупок

Две разные стратегии синхронизации в одном клиенте
  • Клики — optimistic: мгновенный отклик + серверный расчёт и коррекция от Broadcaster (окно не «тормозит»);
  • Покупки — pessimistic: селектор/кнопка блокируются до подтверждения сервера + таймаут на потерянный пакет;
  • Комбо считается локально (click momentum) и унифицируется с серверными значениями без рассинхронов.
04

Синхронизация без «дыр» в данных

Контракт аргументов каждого broadcast-действия
  • BROADCAST_ACTION_CONTRACTS — единый реестр типов аргументов для всех ~80 экшенов стора;
  • Защита от сабой ошибки Luau-один nil в середине списка → сдвиг всех аргументов → коррапт на клиенте;
  • Реестр генерирует список userId-first экшенов — рассинхрон списков физически невозможен.
05

DataStore-жизненный цикл без утечек

ProfileStore + cancellation-флаги вместо Promise.race
  • Таймаут через флаг отмены (а не через утечку сессии в Promise.race);
  • Force-sync profile.Data перед каждым Release(); автосейв через троттлинг-подписку (5 c), а не while(true);
  • Обработка выхода игрока в окне загрузки (pendingCancellations), BindToClose с флешем всех профилей.
06

Производительность: UI и тяжёлые расчеты

Списки не рендерят лишнего, расчёты не крадут кадр
  • useVirtualList — виртуализация по обеим осям, overscan и поддержка переменной высоты элементов;
  • purchaseScheduler — очередь тяжёлых вычислений с бюджетом 4 мс/кадр на Heartbeat (без дедлоков Wait()), LRU-кэш с лимитом;
  • Пул объектов, апдейты горячих значений через refs (dirty-flag), селекторы без лишних ре-рендеров.
07

Повреждённые данные не убьют прогресс

Санитайзер + миграции + проверка конфига на старте
  • Глубокая валидация при загрузке: NaN/Inf, типы, диапазоны, консистентность BigNum-строк;
  • Версионирование схемы Production_v25 + инкрементальные миграции (отдельная ось от имени DataStore);
  • Фатальная проверка конфига при старте: расхождение дефолтов с кодом ловится до продакшена.
