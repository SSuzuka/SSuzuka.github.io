Clicker

Продакшн idle-игра: экономика, бои, кросс-серверная синхронизация — под капотом простого клика.

Подробнее о проекте

Clicker — продакшн idle-игра, где игрок качает героев, бьёт монстров и проходит Ascension за осколки, открывающие новые апгрейды. Полное разделение слоёв — клиент никогда не авторитетен, сервер пересчитывает всё сам. Два независимых стора (Reflex), Broadcaster-синхронизация, BigNum-математика под числа за пределами e15, виртуализация списков карточек героев, object pooling для лута, time-sliced планировщик тяжёлых расчётов, чтобы не подвесить кадр. MemoryStore и MessagingService — под кросс-серверный рейтинг кланов и синхронизацию боевых данных вроде HP между серверами.

Архитектурно — SSoT на сервере, иммутабельный стор на клиенте (Reflex), сервисы и контроллеры через Flamework вместо самодельных синглтонов — событийно, а не поллингом каждый кадр, асинхронщина через Promise, а не callback-цепочки.

Что решал

Реальные рантайм-проблемы — не абстрактные навыки

Без кода — суть проблемы и в какую сторону решено. Код и детали — по запросу, покажу и объясню на пальцах.

проблема

Оплата может подтвердиться Roblox-ом повторно — риск выдать награду дважды.

решение

Каждая оплата запоминается по id; повторное подтверждение не выдаёт награду заново.

проблема

Общий межсерверный босс: несколько серверов бьют одно состояние одновременно.

решение

Урон применяется через атомарное обновление общего состояния, а не через отдельные копии на каждом сервере.

проблема

Игрок выходит и тут же заходит снова, пока данные ещё загружаются — риск получить два процесса на один профиль.

решение

Повторный вход ждёт завершения предыдущей операции вместо запуска параллельно.

проблема

Сервер может упасть в середине операции с валютой — риск потери прогресса или дублирования.

решение

При остановке сервер дожидается завершения активных сохранений, а не отключается мгновенно.

проблема

Дабл-клик или спам одного действия — риск провести операцию несколько раз.

решение

Пока операция не завершена, повторный такой же запрос игрока не запускает новую.

проблема

Клиенту нельзя доверять цену/баланс — можно подменить данные при отправке запроса.

решение

От клиента принимается только само действие, все цифры пересчитываются на сервере заново.

проблема

Клик должен ощущаться мгновенным, но экономика не терпит рассинхрона между вкладками/устройствами.

решение

Клик применяется мгновенно на клиенте (оптимистично), а покупки — только после подтверждения сервера, кнопка блокируется до ответа.

проблема

Валюта в idle-игре легко уходит за пределы точности обычного числа (e15 и выше) — начинаются округления и баги.

решение

Все игровые числа — строки в BigNum-формате со своим движком математики, а не встроенные числа.

проблема

Список из сотен карточек героев в интерфейсе тормозил игру — рендерились все сразу.

решение

Виртуализация: в памяти живут только видимые карточки, остальные не создаются, пока не понадобятся.

проблема

Расчёт «купить максимум» перебирает сотни уровней и может подвесить кадр на середине клика.

решение

Тяжёлые расчёты режутся на порции с бюджетом по времени на кадр, чтобы игра не замирала.

проблема

Наивная обработка таймаута при загрузке профиля игрока приводила к «утечке» сессии — профиль оставался занят.

решение

Загрузка отменяется явным флагом, а не гонкой промисов — профиль корректно освобождается в любом сценарии.

проблема

Нужно было отличать читера с автокликером от игрока с быстрой реакцией, не браня честных игроков.

решение

Лимит скорости действий с запасом на погрешность и «тихий» отказ вместо кика — без ложных банов.

проблема

Передача платных кристаллов между игроками через несколько серверов — потеря подтверждения или повторная доставка могут задвоить баланс.

решение

Внешний журнал операций как единственный маркер коммита: списание и начисление применяются по нему один раз, а не по клиентским подтверждениям.

проблема

Повреждение данных игрока могло молча обнулить купленные за Robux кристаллы вместе с историей покупок.

решение

Независимый ledger чеков покупок: при повреждении профиля донатный баланс, история и статус восстанавливаются, а не теряются.

Падение одной механики не должно ронять всю игру — места, где на кону деньги или данные игрока, я отдельно проверяю на отказ, остальное — обычная разработка без переусложнения.

UI / UX

Интерфейс — это тоже инженерия

UI — не побочный продукт, а такая же инженерная задача, как экономика или сеть. Весь UI проекта написан с нуля, реактивно связан со стором, и подход не зависит от стека — те же принципы работают в любом фреймворке. Ниже — решения, которых потребовала производительность и удобство. Не дублирую то, что уже описано выше (виртуализация списков, оптимистичные и пессимистичные обновления) — только то, чего там нет.

~50 UI-компонентов · 19 хуков игровой логики · адаптив под мобилку и десктоп.

проблема

HP-бар и таймер босса обновляются каждый кадр — через React-состояние это роняет кадр ре-рендерами.

решение

Такие элементы живут вне React: ссылка на DOM-узел и прямое обновление на Heartbeat, причём только когда значение реально изменилось — неизменённые кадры пропускаются.

проблема

Подписка компонента на весь стейт — интерфейс перерисовывается при любом изменении в игре.

решение

Каждый компонент подписан на конкретное значение, а составные данные (статы героев, стоимость покупки) мемоизированы и пересчитываются только когда меняются их входы.

проблема

Один шаблон UI на мобилку и десктоп: на телефоне панели перекрывают игру, на ПК — пустые края.

решение

Разные деревья интерфейса для мобильного и десктопного режима, а размерозависимые модалки монтируются только после того, как движок отдал реальные размеры экрана и врезку топбара — иначе они открываются с кривой геометрией.

проблема

Скроллящиеся списки с рамками у элементов: первая карточка упирается в границу обрезки и рамка режется, полоса прокрутки съедает ширину.

решение

Геометрия окна и канвы скролла разведена явно: у каждого скролла один владелец отступов, проверяются оба состояния (с полосой и без), у крайних элементов — безопасный врез под рамку.

проблема

Тултипы внутри карточек обрезаются границами списков и виртуализацией — карточка исчезла, тултип с ней.

решение

Тултипы рендерятся через портал поверх всего интерфейса, привязаны к реальному положению карточки на экране, а не к её месту в списке.

проблема

Боссы и аномалии выглядят одинаково с обычными монстрами — игрок не видит ценность события.

решение

Состояние монстра (босс, аномалия, свечение ядра) синхронизируется сервером одним пакетом вместе с HP — интерфейс рисует особые состояния без дополнительных запросов, визуальные эффекты (лут, уведомления) идут отдельным каналом и не трогают стейт.

Контракт на аргументы синхронизации

Каждое действие, которое рассылается между клиентом и сервером, сверяется со строгой схемой: если тип аргумента не совпал с ожидаемым — действие отклоняется целиком, а не выполняется со сдвинутыми значениями. Отдельно проверяется, что действие применяется только тому игроку, которому принадлежит — не может прилететь чужому клиенту.

Иллюстрация 
const contract = { amount: "number" };
if (typeof(actual) !== contract.amount) return; // отклонено целиком
if (owner !== player) return;                    // чужое не летит дальше
Детерминированный монстр зоны

Генератор монстра на основе seed от зоны: один и тот же сервер после рестарта всегда выдаёт одного и того же монстра, без необходимости хранить его модель в данных игрока.

Иллюстрация 
const seed = stableHash(zone);
const rng = new SeededRandom(seed); // тот же монстр при том же входе
Ожидание финального сохранения, а не события выхода

Событие «игрок вышел» в Roblox может сработать раньше, чем реально завершится сохранение профиля. Логика ждёт именно завершения сохранения, а не сам факт выхода — иначе можно начать новую сессию поверх ещё не сохранённой старой.

Иллюстрация 
// Ждём факт завершения сохранения, а не событие «вышел» —
// оно может прийти раньше фактической записи.
await profile.onSaved();
Коммит награды в конце цепочки действий

Награда за убийство применяется только после того, как успешно запущен следующий шаг (например, заспавнен следующий монстр). Если по пути произошла ошибка — начисление не происходит, и повторный пакет от клиента не может задвоить награду.

Иллюстрация 
spawnNextMonster();   // сначала — следующий шаг
grantReward();        // награда только если всё выше сработало
// ошибка выше — коммита нет, повтор клиента не задвоит
Защита BigNum от зависания на аномальных данных

Внутренние циклы нормализации больших чисел ограничены по количеству итераций с явным предупреждением, а не оставлены открытыми — на редком крайнем случае это могло бы привести к зависанию, а не просто к неверному результату.

Иллюстрация 
let guard = 0;
while (cond) {
  ...
  guard++;
  if (guard > 3) { warn("аномальный вход"); break; }
}
